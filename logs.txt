================================================================================
PROJECT OVERVIEW
================================================================================

Goal: Create a complete CUDA implementation of BN254 field operations using
      simplified 16-bit arithmetic for educational purposes.

Key Decisions:
1. Use 16-bit limbs (4 limbs = 64-bit) instead of 256-bit for easier debugging
2. Use p = 65521 (largest 16-bit prime) as the field modulus
3. Focus on correctness first, optimization second
4. Provide comprehensive testing and documentation

Phase 2: Type System and Constants (include/bn254_types.cuh)
-------------------------------------------------------------
Implemented:
- limb_t: 16-bit unsigned integer type
- dlimb_t: 32-bit for intermediate calculations
- FieldElement struct with 4 limbs
- Field constants (modulus, Montgomery R, R²)
- Helper functions for element creation and printing
- Error handling macros (CUDA_CHECK, CUDA_CHECK_KERNEL)

Key Features:
- LIMB_BITS = 16
- NUM_LIMBS = 4
- FIELD_MODULUS = 65521 (0xFFF1)
- MONTGOMERY_R = 15 (2^16 mod p)
- MONTGOMERY_R2 = 225 (R² mod p)

Design Rationale:
- 16-bit limbs allow easy verification by hand
- Small prime fits entirely in first limb (simplifies reduction)
- FieldElement methods work on both host and device (__host__ __device__)

Phase 4: CUDA Kernel Implementation (src/field_ops.cu)
-------------------------------------------------------
Implemented all kernels with detailed algorithms:

Helper Functions:
- add_with_carry: Multi-limb addition with carry propagation
- sub_with_borrow: Multi-limb subtraction with borrow propagation
- compare_limbs: Compare two multi-limb numbers
- is_zero: Check if value is zero

Field Operations:
1. Addition Algorithm:
   - Add limb-by-limb with carry
   - Reduce result modulo p
   - Handle overflow cases

2. Subtraction Algorithm:
   - Check if a < b
   - If so, add p first to avoid negative result
   - Subtract limb-by-limb with borrow
   - Reduce result modulo p

3. Multiplication Algorithm:
   - Simplified: Convert to 64-bit, multiply, reduce
   - Full version would use schoolbook or Karatsuba
   - Modular reduction using % operator
   - Result stored back in limb form

4. Montgomery Multiplication:
   - Multiply a * b
   - Apply Montgomery reduction (REDC algorithm)
   - Returns (a * b * R^-1) mod p
   - More efficient for repeated multiplications

5. Montgomery Conversions:
   - to_montgomery: Multiply by R (15)
   - from_montgomery: Multiply by R^-1 (4368)
   - Allows efficient chain of multiplications

Kernel Launch Pattern:
- Grid-stride loop for arbitrary batch sizes
- Block size: 256 threads (good occupancy)
- Thread-per-element parallelism
- Coalesced memory access

Host API Implementation:
- Input validation (null pointers, zero size)
- Automatic grid/block dimension calculation
- Optional CUDA stream support
- Error checking after kernel launch

CPU Reference Implementation:
- Simple, correct implementations
- Used to verify GPU results
- No optimizations (clarity over speed)

Memory Management:
- allocate_device_memory: cudaMalloc wrapper
- free_device_memory: cudaFree wrapper
- copy_to_device: Host to device copy
- copy_from_device: Device to host copy
- All with proper error checking

Device Info:
- print_device_info: Displays GPU properties
  * Device name
  * Compute capability
  * Memory size
  * Multiprocessor count
  * CUDA runtime version

================================================================================
DESIGN DECISIONS & RATIONALE
================================================================================

1. Why 16-bit Limbs?
   - Easy to debug (small values)
   - Fast compilation
   - Clear intermediate results
   - Same algorithms work for 256-bit

2. Why p = 65521?
   - Largest 16-bit prime
   - Fits in single limb
   - Simplifies reduction
   - Good test of overflow handling

3. Why Grid-Stride Loops?
   - Flexible batch sizes
   - Good occupancy
   - Cache reuse
   - Industry best practice

4. Why Both CMake and Makefile?
   - CMake: Professional projects
   - Makefile: Quick testing
   - Different user preferences
   - Learning both systems

5. Why Three Test Suites?
   - Separation of concerns
   - Basic: Correctness
   - Vectors: Batch operations
   - Performance: Optimization

6. Why CPU Reference?
   - Ground truth for verification
   - Easy to understand
   - Confidence in GPU results
   - Debugging aid
